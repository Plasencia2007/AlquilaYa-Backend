# Accesibilidad (A11Y) — AlquilaYa

Guía de referencia para el equipo frontend (`AlquilaYa-Fronted/`). Cubre las
herramientas disponibles, el checklist a pasar antes de cada PR con cambios
de UI, y el proceso manual de prueba con lector de pantalla antes de cada
release.

Este documento nace de la Sección 12 (Accesibilidad) de `MEJORAS.md` — ítems
391, 394, 396, 398, 401, 409, 412, 413, 415. No pretende ser un checklist
WCAG exhaustivo, sino el mínimo práctico para no regresionar.

## Herramientas

| Herramienta | Qué hace | Cómo se usa |
|---|---|---|
| `@axe-core/react` | Audita el árbol de React montado y loguea violaciones en consola del navegador (contraste, labels, roles ARIA, orden de foco…). | Automático en `npm run dev` — ver `src/components/dev/axe-provider.tsx`. Nunca corre en producción. Revisa la consola del navegador mientras navegás la página que tocaste. |
| `scripts/check-contrast.mjs` | Verifica el contraste WCAG AA de los pares fondo/texto de `globals.css` (light y dark). | `node scripts/check-contrast.mjs` desde `AlquilaYa-Fronted/`. Sale con código 1 si algo no llega a AA. No está conectado a CI — corrélo a mano tras tocar `globals.css`. |
| Lighthouse (Chrome DevTools) | Puntaje de accesibilidad + hallazgos automáticos adicionales a axe. | DevTools → Lighthouse → categoría Accessibility. |
| Navegación solo-teclado | Detecta trampas de foco, orden ilógico, elementos sin `:focus-visible`. | `Tab` / `Shift+Tab` / `Enter` / `Escape` por toda la página, sin mouse. |
| Lector de pantalla (NVDA) | Verifica que el contenido se anuncie correctamente. | Ver sección "Prueba con lector de pantalla" más abajo. |

## Checklist por PR

Antes de abrir un PR que toque UI (componentes, páginas, layouts), verificá:

### Labels y semántica
- [ ] Todo `<button>`/`<a>` que sea solo-ícono tiene `aria-label` o texto via `<VisuallyHidden>` (`src/components/shared/visually-hidden.tsx`).
- [ ] Todo `<input>`/`<select>`/`<textarea>` tiene un `<label>` asociado (o `aria-label`/`aria-labelledby` si el label visible no aplica).
- [ ] Las imágenes informativas tienen `alt` descriptivo; las puramente decorativas usan `alt=""` o `aria-hidden`.
- [ ] Los headings (`h1`…`h4`, o `.text-h1`…`.text-h4`) siguen un orden jerárquico razonable dentro de la página — no saltan niveles porque "se veía mejor".

### Foco
- [ ] Cualquier overlay nuevo (modal, drawer, popover con contenido interactivo) usa `Dialog`/`Sheet`/`AlertDialog`/`Popover` de Radix (atrapan foco nativamente) — o, si es un `createPortal` heredado, usa `useFocusTrap` (`src/hooks/use-focus-trap.ts`).
- [ ] Al cerrar un overlay, el foco vuelve al elemento que lo abrió (Radix lo hace solo; `useFocusTrap` también).
- [ ] Ningún elemento interactivo queda con `tabIndex` positivo (rompe el orden natural del DOM).
- [ ] El indicador de foco (`:focus-visible`) es visible sobre cualquier fondo — no lo estás anulando con `outline-none` sin un reemplazo.

### Contraste
- [ ] Si agregaste o cambiaste un color en `globals.css` (tokens `--background`, `--foreground`, `--primary`, etc. en `:root` o `[data-theme="dark"]`), corriste `node scripts/check-contrast.mjs` y pasa.
- [ ] Texto sobre imágenes/fotos tiene un scrim/gradiente que garantice ≥4.5:1 (ver el patrón en `hero-section.tsx`).

### Teclado
- [ ] Todo lo clickeable con mouse es alcanzable y operable con `Tab` + `Enter`/`Espacio` (sin trampas de foco fuera de overlays intencionales).
- [ ] Atajos de teclado custom (ej. flechas en `property-gallery.tsx`) no chocan con la navegación nativa del lector de pantalla ni con `Tab`.

### `aria-live` / anuncios dinámicos
- [ ] Toasts/notificaciones (`sonner`, `notify.*`) — ya anuncian por su cuenta vía el `Toaster`; no dupliques `aria-live` alrededor.
- [ ] Estados de carga async no triviales (spinners de página completa, skeletons de una región) tienen `aria-busy="true"` + un anuncio `sr-only` — usá `<Skeleton label="…">` o `<SkeletonGroup label="…">` (`src/components/ui/skeleton.tsx`) en vez de anunciar cada pieza suelta.
- [ ] Errores de formulario se asocian al campo (`aria-describedby`) y no dependen solo del color.

### Movimiento
- [ ] Cualquier animación nueva con desplazamiento/parallax/autoplay respeta `prefers-reduced-motion` — usá el `useReducedMotion` de `motion/react` si el componente ya usa `motion`, o `src/hooks/use-reduced-motion.ts` si no.

### Copy
- [ ] El texto usa "tú" (no voseo argentino: nada de "recargá", "mirá", "hacé"). Ver ítem 412 de MEJORAS.md.

## Componentes de referencia

| Necesitás… | Usá |
|---|---|
| Saltar navbar/sidebar y llegar al contenido | `<SkipLink href="#contenido" />` (`src/components/shared/skip-link.tsx`) — ya montado en los 4 layouts raíz. |
| Texto solo para lector de pantalla | `<VisuallyHidden>` (`src/components/shared/visually-hidden.tsx`), en vez de repetir `className="sr-only"` inline. |
| Detectar `prefers-reduced-motion` fuera de `motion/react` | `useReducedMotion()` (`src/hooks/use-reduced-motion.ts`). |
| Atrapar foco en un overlay `createPortal` heredado | `useFocusTrap()` (`src/hooks/use-focus-trap.ts`). |
| Skeleton con semántica de carga | `<Skeleton label="Cargando propiedades…">` o `<SkeletonGroup label="…">` (`src/components/ui/skeleton.tsx`). |

## Prueba con lector de pantalla (NVDA)

Antes de cada release (no en cada PR — es un proceso manual, no automatizable
desde CI), un humano del equipo debe correr estos 3 flujos críticos con
**NVDA** en Windows + Chrome o Firefox. Instalación: [nvaccess.org](https://www.nvaccess.org/download/).

Atajos NVDA útiles durante la prueba:
- `Insert + ↓` — leer desde el cursor virtual.
- `Tab` / `Shift+Tab` — moverse entre elementos enfocables.
- `H` / `Shift+H` — saltar entre encabezados (con NVDA en modo navegación).
- `Insert + F7` — listar links/headings/landmarks de la página.
- `Insert + T` — leer el título de la pestaña/ventana activa.

### Flujo 1 — Buscar y reservar (rol estudiante)

1. Entrar a `/` con NVDA activo. Confirmar que el primer `Tab` enfoca el
   **skip link** ("Saltar al contenido") y que activarlo mueve el foco al
   `<main>`, saltando navbar completo.
2. Usar el buscador del hero (zona, tipo de cuarto, botón "Buscar"). Confirmar
   que el Combobox de zonas anuncia las opciones al navegar con flechas y que
   el `Select` de tipo anuncia el valor elegido.
3. En `/search`, confirmar que los resultados (cards de propiedad) se anuncian
   con datos suficientes (título, precio, zona) al tabular por ellos — no solo
   "enlace" sin contexto.
4. Entrar al detalle de una propiedad (`/property/[id]`). Abrir la galería en
   pantalla completa (`property-gallery.tsx`): confirmar que el foco entra al
   lightbox, `Tab` queda atrapado dentro (no se escapa al fondo), y `Escape`
   cierra devolviendo el foco al thumbnail que lo abrió.
5. Iniciar sesión (o registrarse, ver Flujo 2) y completar una reserva.
   Confirmar que el formulario de reserva anuncia errores de validación
   asociados a cada campo, y que la confirmación de éxito se anuncia (no solo
   visual).
6. Completar el pago (o simularlo en dev con `POST /pagos/simular-exito/{id}`)
   y llegar a `/pago/exito`. Confirmar que el confeti (si `prefers-reduced-motion`
   no está activo) no interfiere con el foco ni genera anuncios repetidos, y
   que el estado de éxito se anuncia claramente.

### Flujo 2 — Registrarse

1. Ir a `/register`. Confirmar que cada campo del formulario multi-paso tiene
   label asociado y que el paso actual se anuncia (ej. "Paso 2 de 3").
2. Provocar un error de validación (ej. contraseña débil, campo vacío) y
   confirmar que NVDA lo anuncia inmediatamente al perder foco o al intentar
   avanzar — no solo un borde rojo silencioso.
3. Completar el registro hasta el paso de verificación OTP (WhatsApp).
   Confirmar que el input OTP (`input-otp`) es operable y anunciado dígito a
   dígito de forma coherente, no como una masa de inputs sin contexto.
4. Confirmar que la redirección final tras verificar el OTP se anuncia (nuevo
   título de página / nuevo heading principal detectable con `H`).

### Flujo 3 — Chatear (mensajería)

1. Como estudiante o arrendador, entrar a la sección de mensajes
   (`/student/messages` o `/landlord/messages/students`). Confirmar que la
   lista de conversaciones se navega con `Tab`/flechas y cada ítem anuncia
   remitente + preview del último mensaje + no-leídos si aplica.
2. Abrir una conversación y enviar un mensaje por WebSocket (STOMP). Confirmar
   que el mensaje enviado y los mensajes entrantes en vivo se anuncian vía
   una región `aria-live="polite"` (no requieren que el usuario navegue
   manualmente para enterarse de un mensaje nuevo) — si NO se anuncian, es un
   hallazgo a reportar, no algo que este documento asuma resuelto.
3. Confirmar que el campo de texto para escribir tiene label/placeholder
   anunciado y que el botón de enviar es alcanzable por teclado sin atajos
   de mouse (drag & drop de adjuntos, si existe, debe tener alternativa por
   teclado o quedar documentado como pendiente).
4. Cerrar la conversación / volver a la lista y confirmar que el foco no se
   pierde (vuelve a un lugar predecible, no al `<body>`).

### Registrar hallazgos

Cualquier problema encontrado en estos 3 flujos se agrega como ítem nuevo en
`MEJORAS.md` (Sección 12) con el flujo, los pasos para reproducir y el
comportamiento esperado — no se corrige "silenciosamente" sin dejar rastro,
salvo que sea un fix trivial de una sola línea (ej. `alt` faltante).

## Hallazgo actual de `check-contrast.mjs` (2026-07-28)

La primera corrida del script sobre `globals.css` ya encontró 3 fallos reales
en el **tema dark** (el tema light pasa limpio):

| Par | Ratio | Mínimo AA | Uso típico |
|---|---|---|---|
| `primary` / `card` | 3.13:1 | 4.5:1 (texto normal) | `#c14b4c` sobre `#2e2330` — pasa como texto grande/ícono (≥3:1) pero NO como texto normal. |
| `primary-foreground` / `primary` | 3.54:1 | 4.5:1 (texto normal) | `#231924` sobre `#c14b4c` — texto de botón primario en dark. |
| `accent-foreground` / `accent` | 4.06:1 | 4.5:1 (texto normal) | `#c1999b` sobre `#4a3c4d` — texto sobre superficie de acento en dark. |

No se tocó `globals.css` para corregir esto en la misma pasada que agregó el
script (cambiar la paleta de marca es una decisión de diseño, no algo para
resolver de paso). Queda como ítem a evaluar: o bien esos tokens solo se usan
hoy en contextos de texto grande/ícono (en cuyo caso el fallo es un falso
positivo del check genérico y se puede anotar como excepción), o hay que
ajustar el tono en dark. Correr `node scripts/check-contrast.mjs` para
confirmar el estado actual.

## Pendiente / documentado pero no implementado

- **`aria-live` en el chat en vivo**: no confirmado que los mensajes STOMP
  entrantes se anuncien automáticamente — ver Flujo 3, paso 2. Si la prueba
  NVDA lo confirma como hallazgo, pasa a MEJORAS.md como ítem nuevo.
- **`prefers-reduced-motion` en el 100% de las animaciones**: los componentes
  de `src/components/motion/*` (usados por la mayoría de secciones del home,
  búsqueda y dashboards) y el confeti de pago exitoso ya lo respetan. El Ken
  Burns del hero está gateado a nivel CSS (`@media (prefers-reduced-motion: no-preference)`
  en `globals.css`). Componentes de animación más nuevos o con `motion.div`
  directo (fuera de `src/components/motion/*`) deben revisarse caso a caso —
  no se auditó el 100% del árbol de componentes.
- **`check-contrast.mjs` en CI**: fuera de alcance por ahora (ver ítem 398 de
  MEJORAS.md) — es una verificación manual. Conectarlo a un workflow de
  GitHub Actions queda como trabajo futuro.
- **Migración completa de `createPortal` a Radix**: los overlays heredados
  listados en el checklist de PR (validaciones de proveedores, revisión de
  propiedades, moderación de reseñas/mensajes, roles personalizados, perfil
  de estudiante en reservas, preview de documentos KYC, lightbox de galería)
  ya tienen `useFocusTrap` aplicado, pero seguir usando `Dialog`/`Sheet` de
  Radix para overlays nuevos sigue siendo la recomendación — no se migraron
  los existentes a Radix en esta pasada (cambio de mayor alcance, fuera del
  ítem 396 tal como se planteó).
